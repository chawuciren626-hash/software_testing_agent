# 设计系统视角审阅：测试智能体控制台

> 审阅对象：`web_console/templates/index.html`（2592 行，150KB）
> 审阅视角：**设计系统架构**（token 体系 / 尺度系统 / 组件一致性 / 视觉语言）
> 与 `docs/UI_UX_REVIEW.md` 的关系：那份是**工程与合规视角**（a11y、路由、响应式、交互），
> 本文是**设计语言视角**（尺度、色彩体系、组件契约）。两者互补，不重叠。
> 所有数值均为脚本实测，非目测估计。

---

## 1. 一句话结论

**这个控制台的「色彩」已经是一个设计系统，「尺度」完全不是。**

颜色有 25 个 token、296 处引用、覆盖率 84%；而字号 17 档、圆角 16 档、间距 20 档且**间距 token 数量为 0**。
结果是：改一次主题色只需动 1 处，改一次全局间距需要人肉搜改 98 处且必然漏。

好消息是：**架构底子是对的**（token 已存在、组件已收敛、`.card`/`.btn`/`.badge` 已成体系）。
这不是"推倒重来"，是**把已有的一半补完**。

---

## 2. 设计基线实测

| 维度 | 实测 | 健康值 | 判定 |
|---|---|---|---|
| 颜色 token | 25 个 / 296 处引用 | — | 良好 |
| 硬编码 HEX | 44 种 / 58 处 | ≤ 10 处 | 需收口 |
| 字号档位 | **17 种 / 98 处** | 6–7 档 | 失焦 |
| 圆角档位 | **16 种** | 5–7 档 | 失焦 |
| 间距档位 | 20 种 / **token 0 个** | 7 档全 token | 缺失 |
| 字重 | 5 种（400/500/600/700/800） | 4 种 | 可收敛 |
| 阴影 | 26 处 / **token 2 个** | 5 档 | 缺中间档 |
| z-index | 4 个值（50/55/60/200） / token 0 | 全 token | 缺失 |
| 内联 `style=` | 92 处 | ≤ 20 | 需收敛 |

### 2.1 最有说服力的一组证据：字号

```
 9px  2处   10.5px  2处   11px 17处   11.5px  8处
12px 21处   12.5px 13处   13px 14处   13.5px  3处
14px  5处   14.5px  1处   15px  2处   15.5px  3处
16px  1处   17px    3处   19px  1处   25px   1处   26px 1处
```

**9px 到 13.5px 之间挤了 8 档**，其中 `12 / 12.5 / 13 / 13.5` 四档相邻只差 0.5px。
0.5px 在 1x 屏上会被舍入成同一个像素值 —— 也就是说这些"档位"**在多数屏幕上根本不产生视觉差异**，
它们不是设计决策，是历史累积的噪音。

## 3. 核心问题（按修复杠杆排序）

### P1 · 间距零 token —— 最大杠杆

`--radius` 和 `--shadow-*` 有 token，**间距一个都没有**。20 种数值全部硬编码在组件里：
`14`(9处) `9`(6处) `10`(5处) `8`(5处) `20`(4处) `12`(4处) `6`(4处) `1`(4处) `18`(3处) `16`(3处) `26`(2处) `11`(2处) `7`(2处)

后果：想让全局"松一点"或"紧一点"，只能逐组件搜改。这是最典型的、也是最容易在迭代中失控的债务。

**建议：4px 基准网格，7 档**

```css
:root{
  --sp-1:4px;  --sp-2:8px;  --sp-3:12px; --sp-4:16px;
  --sp-5:20px; --sp-6:24px; --sp-8:32px;
}
```

| 现值 | 归位 | 现值 | 归位 |
|---|---|---|---|
| 1, 2 | `--sp-1` (4) | 14 | **逐处人工判定** 12 或 16 |
| 6, 7, 8, 9, 10 | `--sp-2` (8) | 16 | `--sp-4` |
| 11, 12 | `--sp-3` (12) | 18, 20 | `--sp-5` (20) |
| | | 26 | `--sp-6` (24) |

> ⚠️ **14px 不要批量替换**。它出现 9 次、是卡片内间距的主力值，且用户刚反馈过"卡片太挤"。
> 归 12 会更挤、归 16 会松，必须逐处看。诚实做法是留作人工项，不进批量脚本。

### P2 · 字号 17 档 → 6 档

```css
:root{
  --fs-display:26px;  /* 统计大数字 */
  --fs-title:17px;    /* 页面标题 h1 */
  --fs-lg:15px;       /* 区块标题、卡片标题 */
  --fs-base:13px;     /* 正文 */
  --fs-sm:12px;       /* 次要信息、表格 */
  --fs-xs:11px;       /* 徽标、辅助说明 */
}
```

| 新档 | 收编原值 | 处数 |
|---|---|---|
| 26 | 25, 26 | 2 |
| 17 | 17, 19 | 4 |
| 15 | 14.5, 15, 15.5, 16 | 7 |
| 13 | 13, 13.5, 14 | 22 |
| 12 | 12, 12.5 | 34 |
| 11 | 9, 10.5, 11, 11.5 | 29 |

合计 98 处，与实测总数吻合，无遗漏。

### P3 · 圆角 16 档 → 7 档

```
--r-xs:3px     (收 2, 3        → 3处)
--r-sm:6px     (收 4, 5, 6     → 7处)
--r-md:10px    (收 8,9,10,11,12→ 27处)   ← 主力档
--r-lg:14px    (卡片，沿用现 --radius)
--r-xl:20px    (收 16, 18, 20  → 4处)
--r-pill:999px (收 999px       → 6处)
--r-full:50%   (收 50%         → 4处)
```

⚠️ 现 `--radius:14px` / `--radius-sm:9px` 的命名与新档位冲突（`--radius-sm` 现在是 9px 而新体系里 sm=6px）。
建议：新体系用 `--r-*`，旧的 `--radius*` 保留为别名过渡，全部替换完再删。

### P4 · 深色侧栏是「第二个主题」，但没有 token

侧栏是独立的深色世界，却全部硬编码：

```css
.sidebar{background:linear-gradient(180deg,#0f172a 0%,#111c33 100%);color:#cbd5e1;}
.brand{border-bottom:1px solid rgba(148,163,184,.12);}
```

**建议：把深色区建成完整的 surface token 组**

```css
:root{
  --nav-bg:#0f172a;          --nav-bg-2:#111c33;
  --nav-text:#cbd5e1;        --nav-text-muted:#8b9ab3;
  --nav-border:rgba(148,163,184,.14);
  --nav-hover:rgba(255,255,255,.06);
  --nav-active:rgba(99,102,241,.16);
}
```

**顺带一个审美建议**：`linear-gradient` 深色侧栏是 2019 年的 SaaS 套路，
与这套设计的实际气质（Linear / Vercel 谱系的扁平克制）**是冲突的**。
建议改成纯色 `--nav-bg`，渐变用在品牌 logo 上就够了（那里保留是合适的，它是品牌标识不是背景）。
这是零风险改动，一行的事。

### P5 · 组件变体：维度混在修饰符里

实测 `.btn` 的 9 种组合：

```
btn 13   btn sm 14   btn tab sm 9   btn primary 8   btn sm primary 2
btn primary block 1   btn tab sm active 1   btn ghost sm 1   btn sm danger 1
```

`tab` 是**形态**、`sm` 是**尺寸**、`primary/danger` 是**语义**、三者混在同一层修饰符里。
`btn tab sm` 出现 9 次说明 tab 其实是另一个组件，不该寄生在 btn 上。

**建议拆维度**：

```css
/* 尺寸 */ .btn--sm{padding:6px 11px;font-size:var(--fs-sm);}
/* 语义 */ .btn--primary{} .btn--danger{} .btn--ghost{}
/* 形态 */ .btn--block{width:100%;}
/* tab 独立成组件 */ .tab{} .tab.is-active{}
```

同类问题在 `badge` 上也有：`gray` 与 `none` 语义重叠（都表示"无状态"），建议合并为一个 `neutral`。

### P6 · 表格无统一规则

全文 12 个 `<table>`，但全局 `th/td` 规则只有 2 条 —— 意味着每个表格各自写样式。
建议统一一个 `.tbl` 契约（这也是 `UI_UX_REVIEW.md` 第 11 项的内容，两视角结论一致）：

```css
.tbl{width:100%;border-collapse:collapse;font-size:var(--fs-sm);}
.tbl th{position:sticky;top:0;background:var(--panel);
        text-align:left;font-weight:600;color:var(--muted);
        padding:var(--sp-2) var(--sp-3);border-bottom:1px solid var(--border);}
.tbl td{padding:var(--sp-2) var(--sp-3);border-bottom:1px solid var(--border-2);}
.tbl td.num{font-variant-numeric:tabular-nums;text-align:right;}
```

`tabular-nums` 对测试报告页（大量数字列对齐）收益明显。

### P7 · 阴影缺中间档

26 处 `box-shadow` 只有 `--shadow-sm` / `--shadow-md` 两个 token，弹窗和卡片 hover 各写各的。
建议补齐 5 档：

```css
--shadow-xs:0 1px 2px rgba(15,23,42,.04);
--shadow-sm:0 1px 2px rgba(15,23,42,.04), 0 1px 3px rgba(15,23,42,.05);
--shadow-md:0 1px 2px rgba(15,23,42,.04), 0 8px 24px rgba(15,23,42,.07);
--shadow-lg:0 12px 32px rgba(15,23,42,.10), 0 2px 8px rgba(15,23,42,.06);
--shadow-xl:0 24px 48px rgba(15,23,42,.16);
```

配套 z-index token：`--z-sticky:50; --z-drawer:55; --z-modal:60; --z-toast:200;`（沿用现有数值，不变更层级关系）。

### P8 · 冗余与不一致（顺手清）

- `--ink:#0f172a` 与 `--text:#0f172a` **同值重复** → 合并为 `--text`，`--ink` 留别名。
- 字重 5 种 → 收敛 4 种（400 / 500 / 600 / 700），`800` 只保留给 `--fs-display`。
- 44 种硬编码 HEX 里，多数是 token 的**复制品**（如 `#d1fae5` 就是 `--ok-soft`）→ 批量替换为 `var()`。
- 92 处内联 `style=` → 优先清理布局类（`width`/`margin`/`display`），动态值（进度条、状态色）保留。

## 4. 建议的 token 体系结构

```
原始层    HEX 色值 · px 数值 · 无意义命名（--ok-soft:#d1fae5）
   ↓
语义层    按用途命名（--color-surface / --space-card / --radius-control）
   ↓
组件层    只吃语义 token，不得直取原始层（.card{padding:var(--space-card)}）
   ↓
页面层    零硬编码，只组合组件
```

**当前卡在第 1 层**：颜色有语义层，尺度连原始层都没有。补完顺序建议：**间距 → 字号 → 圆角**。

---

## 5. 落地路线（两批）

### 第一批：建立尺度系统（纯增量，约 1 轮）

1. 加 `--sp-*` / `--fs-*` / `--r-*` 三组 token（只新增，不改任何组件 → **零视觉变化、零风险**）
2. 加 `--nav-*` 深色区 token
3. 补 `--shadow-lg/xl` 与 `--z-*`
4. 侧栏渐变 → 纯色（审美对齐，1 行）

验证方式：改前后截图逐像素比对，应**完全一致**（只有第 4 项有可见变化）。

### 第二批：组件消费 token（需逐个验证）

5. 字号 98 处归 6 档（可脚本批量 + 抽样目检）
6. 圆角 16 档归 7 档（**`14px` 卡片档需人工确认**）
7. 间距 20 档归 7 档（**`14px` 逐处人工判定，不进批量脚本**）
8. 44 处硬编码 HEX → `var()`
9. 按钮拆维度 / tab 独立成组件
10. 表格统一 `.tbl` 契约 + sticky + `tabular-nums`
11. badge `gray`/`none` 合并为 `neutral`
12. 92 处内联样式收敛（布局类优先，动态值保留）

> 第 5–8 项建议**一次只做一个维度**，每做完一个跑一次测试 + 截图比对。
> 一次性全改，出问题无法定位是哪个维度。

## 6. 值得保留的设计决策（重构时别误伤）

1. **`:root` 里那条对比度注释** —— 记录了"改色必须重算对比度"的约束及原因。这是本次审阅见到的最有价值的 4 行注释，删了下次还会踩。
2. **卡片用 `flex-direction:column` + `gap`，而非 margin 堆叠** —— 天然免疫 margin 折叠，且插删元素不影响间距。
3. **`.grid` 用 `auto-fill + minmax(360px,1fr)`** —— 无媒体查询就自适应，思路正确，只是没推广到骨架。
4. **语义色成对定义（`--ok` + `--ok-soft`）** —— 文字色与底色绑定，改主色不会破坏对比度。这是高级做法，很多团队做不到。
5. **深色侧栏 + 浅色内容区的双 surface 架构** —— 信息密度高的工具类产品的正确选择，不要为了"统一"改成全白。
6. **`--sans` 字体栈把 `PingFang SC` / `Microsoft YaHei` 放在系统字体之后** —— 中文渲染优先级正确，别改成把中文放最后。
