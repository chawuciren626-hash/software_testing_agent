## 2. 现状事实（已核查）

- `agent-skills/` 下 **6 个静态技能**：`api-test-design` / `ci-gate-design` / `qa-test-design` /
  `requirements-to-cases` / `software-testing` / `web-automation`。
- 每个 `SKILL.md` 有前置元数据 `name` + `description`，但**没有 `version` 字段**。
- **没有任何代码扫描或加载 `agent-skills/`** —— 它目前只是"放那儿的目录"，产品运行时并不感知。
- 仓库版本在 `pyproject.toml`：`version = "0.2.0"`（这是**仓库版本**，与单个技能的版本是两回事）。

## 3. 已落地：本地地基（A 块）

新增 `extensions/skills/registry.py` + 包 `__init__.py`：

- **自动发现**：`discover_skills()` 扫描 `agent-skills/` 各子目录的 `SKILL.md` 前置元数据，无需手工登记。
- **版本声明**：每个技能在 `SKILL.md` 前置元数据加了 `version: 0.1.0`（独立语义化版本，不跟仓库版本走）。
- **版本目录**：`build_catalog()` 汇总成 `agent-skills/skills_catalog.json`（相对路径，可提交、跨机可读），
  供控制台 / 未来市场读取。
- **CLI**：`python extensions/skills/registry.py --catalog agent-skills/skills_catalog.json` 可重新生成目录。
- **防漂移测试**：`tests/test_skill_registry.py` 校验「提交的目录 == 当前发现结果」，改了技能忘了 regenerate 会让 CI 红。

> 这套地基对 B 块的两个选项都通用——无论你最后选自托管还是公共市场，发现器与版本字段都是前置依赖。

## 4. 待决策：B 块（市场接入 + 版本分发）

下面三个方案，差别只在"技能从哪来、怎么升级"，**本地能力与质量不受影响**。

### 方案 1 · 不接市场，纯本地（推荐起步）
- 技能就放在本仓库 `agent-skills/`，靠 git 版本控制 + 上面的 `skills_catalog.json` 做清单。
- 升级 = 改技能文件 + 改 `version` + 提交。消费方（本智能体）直接读本地目录。
- **优点**：零外部依赖、零运维、与现有仓库流程一致；最快落地。
- **缺点**：跨项目 / 跨团队复用要手动拷；没有"一键更新"。
- **适用**：当前单人 + 本项目阶段。

### 方案 2 · 自托管技能仓库（Git Submodule / 独立 repo + release）
- 技能抽到独立 git 仓库（或 submodule），用 **Git tag = 版本**（`v0.1.0`）做发布点；
  `skills_catalog.json` 增加 `repo` + `tag` 字段，消费方按 tag 拉取固定版本。
- **优点**：跨项目复用、版本可追溯、可回滚到任意 tag；仍不依赖任何第三方平台。
- **缺点**：要维护第二个仓库 + 发布流程；submodule 有学习成本。
- **适用**：技能要被多个项目 / 团队共用时。

### 方案 3 · 公共市场（如 WorkBuddy 技能市场）
- 技能按平台规范打包、上架，消费方通过市场 API 搜索 / 安装 / 升级。
- **优点**：可发现性最强、生态复用；平台可能提供签名 / 审核。
- **缺点**：依赖平台可用性、账号、审核节奏；需适配平台打包格式；**数据出境 / 合规需评估**（你做测试项目的技能可能涉及内部接口约定，上公共市场要脱敏）。
- **适用**：技能希望对外公开、形成生态时。

**默认推荐**：先 **方案 1** 跑通（已落地），等确实要跨项目复用了再升 **方案 2**；方案 3 仅在技能确认可对外、且合规评估通过后才考虑。
