# 测试门禁设计技能

## 适用场景
- 要给一个测试项目加 CI 门禁（回归 / 接口 / 性能 / Web 冒烟）：判什么、什么算通过、失败了怎么通知。
- 已有流水线但"永远绿"或"永远红"，需要定位口径问题。
- 审查别人的门禁设计是否可信。

## 一、核心原则：门禁只有两种失效方式，都很贵

| 失效方式 | 表现 | 代价 |
|---|---|---|
| **假绿**（更危险） | 门禁通过，但实际没验什么 | 缺陷流到生产；团队从此不再相信"绿" |
| **假红** | 门禁失败，但实际没问题 | 红色变成噪音；团队习惯性忽略红 |

好的门禁设计=同时压制这两种。下面每条都是为压制其中之一而存在的。

## 二、三态判定（不是两态）

不要用「通过 / 失败」两态。至少四档：

| 状态 | 含义 | 是否算门禁达成 |
|---|---|---|
| ✅ 通过 | 有产物且 `all_pass: true` | 是 |
| ❌ 未通过 | 有产物且 `all_pass: false` | 否 |
| ⏭ **未执行** | 声明了门禁但没跑（无产物/产物损坏/被跳过） | **否**（未执行 ≠ 通过） |
| — **未配置** | 项目根本没声明这道门禁 | **不参与判定** |

- 「未执行 = 否」专治假绿：**"没有失败" 不等于 "通过"**。
- 「未配置 = 不参与」专治假红：项目压根不用 Web 冒烟，却因为没跑 Web 而判红，是把红色变成噪音的典型做法。
- 结论优先级：**未通过 > 未执行 > 通过**。

## 三、分流：环境问题 ≠ 产品缺陷

必须严格区分，混为一谈会产生两种坏结果：

| 现象 | 正确判定 | 判错会怎样 |
|---|---|---|
| 连接被拒 / DNS 失败 / 超时连不上 | SKIP（环境不可达） | 判 FAIL → "服务没起"被报成一堆用例失败，排查被带偏 |
| 浏览器起不来 / 驱动缺失 | SKIP | 同上 |
| HTTP 4xx / 5xx（服务在线，正常返回错误） | **FAIL（产品缺陷）** | 判 SKIP → 应用 500 被当"环境抖动"悄悄放过 |
| 业务码失败（HTTP 200 但 body `code=500`） | **FAIL** | 只看 HTTP 状态 → 密码错了也判通过（经典假绿） |

补充两条：
- **基线探测**：跑任何场景前先探一次目标可达性。**基线不通过就不要逐个执行场景** ——
  否则"服务没起"会退化成"每个场景都失败"，报告里全是 FAIL，真正的根因反而看不见。
- **配置错误单独报出，且该场景不执行**：脆弱定位器、未知步骤、缺参数。静默跳过 = 悄悄放松门禁，
  这是最危险的失败模式；混进产品缺陷里 = 把配置笔误当 bug 报给开发。

## 四、断言有效性：没有断言的门禁是装饰

- 声明的场景/用例**至少要有一个真实断言**，否则记 SKIP（不算绿）。
  "点完就走、永远通过"的用例放进门禁是负资产。
- **抗抖动与诚实要平衡**：`retries` 默认 0 —— 重试会吃掉偶发缺陷的证据。
  需要抗抖动时，重试后通过的用例仍标 `flaky` 并单独计数，**不藏抖动**。
- **证据必须属于本次运行**：运行前清理上次的截图/复现脚本，否则旧证据会被当成本次证据，排查误导极大。
- 失败要留可复现证据：截图 + 可执行的复现脚本（如 Playwright `.spec.ts`）。

### 四之补：被忽略的状态必须全视图口径一致（"幽灵红"）

项目常有"停用 / 归档 / 跳过"这类状态标记。**只要有一个视图没读到这个标记，就会产生幽灵红**：
停用的项目还留着上次的失败产物 → 门禁持续判红，而项目列表里又看不到它（因为列表读了这个标记）
→ 用户看到一个无法解释的红色，最后学会忽略红色。

实测踩过：`load_projects()` / 跨项目看板 / 控制台项目页都会跳过 `.disabled` 项目，
但门禁摘要模块是直接遍历目录的，没读这个标记 → 停用项目仍在拖门禁。

规则：
- 新增任何"汇总/判定"入口时，都要走**与列表同样的过滤**，不要自己 `iterdir()`。
- 过滤要**如实交代**：摘要里写明"已跳过 N 个停用项目：xxx"，静默隐藏会让人以为"全都算过了"。
- 只隐藏、不交代，和假绿是同一类问题。

## 五、结果落盘与通知

- 每类门禁写独立产物 JSON（含 `all_pass` / `summary` / 明细），门禁判定与通知都**只读产物**，
  不要重新执行 —— 避免"判定时重算一遍"导致结论与报告不一致。
- 判定口径必须**单一来源**：CLI、报告、Web、通知全部调用同一个函数。
  **两套判定口径比没有判定更糟**（会让人不再相信任何一个）。
- 摘要要人话：N 个项目 / 通过 / 未通过 / 未执行 + 逐项目逐门禁状态 + 失败原因。
- 通知的**硬门禁判定与发送解耦**：`--dry-run` 必须不发通知 ——
  否则没有凭据就没法测这段逻辑，只能靠"发一次看看"，代价是骚扰收件人。
- 无凭据时打印"跳过通知"而非报错，让流水线在未配置通知的情况下也能验证。

## 六、GitHub Actions 落地的真实坑

1. **workflow 必须在仓库根 `.github/workflows/`**。放进子目录（如 `extensions/xxx/.github/workflows/`）
   会被**完全忽略** —— 表现是"我明明写了 CI 却从来没有运行记录"，且没有任何报错。
   这是最容易发生、最难发现的一个。
2. **不要用 `|| true` 吞测试失败**。它把门禁变成装饰：红了也没有测试结论，排查时极易误判成代码问题。
   要区分"必须过"和"仅供参考"，用**独立作业 + `continue-on-error`**，而不是在 pytest 后面加 `|| true`。
3. **一套作业只跑一个项目的门禁时，判定必须过滤到那个项目**。
   否则同一仓库里其余"从未跑过"的项目全记「未执行」→ 门禁**永远红**且看不出原因。
4. **运行期目录不入库时，全新 checkout 里没有任何项目**。要么在 CI 里先登记（`create ... --force`），
   要么显式跳过 —— 否则门禁在 CI 里永远拿不到被测目标。
5. **依赖只装必要的，但不能漏**。装得越多，越容易因为某个重依赖"装不动"而红。
   但反过来也要注意：**一个跑整个 `tests/` 目录的作业，必须装齐所有依赖** ——
   哪怕它是「非门禁」作业。实测踩过：某作业只装被测项目自身的包依赖，而 `tests/` 里的用例
   `import flask / requests / pytest`，结果作业因为「缺 pytest」这种与代码无关的原因变红。
   非门禁的噪音红同样有害：它会让人习惯性忽略红色。
   → 拆分作业时，按「跑哪些测试文件」反推依赖，而不是按「测哪个包」。
   → 布置好后做一次**静态审计**：AST 扫出 CI 范围内所有文件的第三方顶层 import，
     与依赖清单逐个比对（注意包名≠import 名，如 `pyyaml`→`yaml`、`python-dotenv`→`dotenv`、
     `allure-pytest`→`allure`）。比等 CI 红了再猜快得多。
   → 更强的做法：**本地用只装 CI 依赖清单的干净环境照抄 CI 命令跑一遍**。
     这能在推送前就发现"依赖不够"和"隐藏 import"，是唯一能在本地逼近 CI 结果的手段。
6. **未配置环境变量时显式警告并跳过，不静默判绿**。用 `::warning::` 让跳过**可见**。
7. **多道门禁用 `continue-on-error` 收齐全部结论后再统一判定**。第一道失败就中断，会丢掉其余几道的结果，
   排查时还得重跑一遍。
8. **通知作业是全新 checkout**，没有上游产物 —— 重算只会得到"无项目"这种废话。应通过 artifact 复用上游摘要。
9. 装机坑：Allure 的 pytest 插件包名是 **`allure-pytest`**，不是 `pytest-allure`（后者在 PyPI 不存在，
   会让 install 阶段直接失败，表现为"流水线红了但没有任何测试结论"）。

## 七、审查清单（给自己或别人的门禁打分）

- [ ] 门禁判定是三态还是两态？"未执行"会被算成通过吗？
- [ ] 未配置的门禁会不会被判红（制造假红噪音）？
- [ ] 环境不可达与 HTTP 错误是否分流？业务码（HTTP 200 + 业务失败）是否会被误判为通过？
- [ ] 有没有"无断言 / 点完就走"的用例混在门禁里？
- [ ] 失败证据是不是本次运行的？（旧的有没有被清理）
- [ ] 重试是否掩盖了偶发缺陷？flaky 有没有被单独计数？
- [ ] CLI / 报告 / Web / 通知的判定口径是不是同一个函数？
- [ ] 没配置密钥时，通知逻辑还测得了吗（有没有 `--dry-run`）？
- [ ] workflow 在仓库根吗？有没有 `|| true`？未配置时是警告还是静默跳过？
- [ ] 汇总/判定入口有没有走"停用/归档"过滤，和列表页口径一致吗？跳过的人有没有被交代？
- [ ] 每个作业安装的依赖，够不够它实际要跑的测试文件 import？（非门禁作业也一样）
- [ ] 新增的门禁测试**能不能失败**？注入一个明显的错误验证它会变红 ——
      不会失败的测试只是装饰，还会给人"有覆盖"的错觉。

## 本仓库的参考实现
- `extensions/reporting/gate_notify.py`：三态汇总 + 通知（`--dry-run` / `--fail-on-gate` / `--project`）。
- `extensions/regression/run_regression.py`：核心回归门禁（`all_pass = failed==0 and passed>0`）。
- `extensions/perf_security/run_perf_security.py`：性能阈值门禁 + 6 项安全检查（含基线校验防假漏洞）。
- `extensions/web_testing/run_web.py`：声明式浏览器门禁（无断言不计绿、连接级错误与 HTTP 错误分流）。
- `.github/workflows/ci.yml`：硬门禁 / 非门禁 / 项目级门禁 / 通知 四作业结构。
- 控制台「门禁」页（`GET /api/gates`）：与 CLI 同源同口径的可视化。
